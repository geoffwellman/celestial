### Changed
- The guard reads a command line as bash does, for every rule and every adapter (claude, omp/pi, OpenCode): a newline ends a command, like `;`. A newline inside a quoted string and a comment are data. A heredoc body (`<<EOF`, `<<-EOF`, `<<'EOF'`) is data only when its reader is a data sink. A sink is the command given the body and everything it pipes into, a `while read ... done` loop included, when each is cat, tee, `cel`, read, jq, echo, grep or the like, `git commit -F -` or `gh ... --body-file -`, and no file it writes is run later in the line. Even then, the `$(...)` and backquotes an unquoted heredoc expands are commands. Any other reader makes the body commands: a shell, python, node, perl, `$SHELL`, a loop that runs its lines. So does a string that is code for a shell (`bash -c`, `sh -c`, `$'...\n...'`, eval, ssh). Arithmetic (`$((..))`, `((..))`, `$[..]`, a subscript) opens no heredoc. A line the guard cannot be sure of is read the cautious way, every newline separating commands: an unclosed quote or heredoc, a delimiter with `$`, `[` or `]`, or a `<<` inside a subscript.
- The claude hook now classifies a shell command through `guard-classify.sh`, as omp/pi and OpenCode do. In the claude and omp/pi adapters a classifier that does not finish within `CEL_GUARD_TIMEOUT` seconds (default 10; omp/pi's limit was 3 s) refuses the call instead of allowing it. OpenCode already refused one (15 s).
- The guard normalises a line's commands in one pass, so a long multi-line command costs about what it did before.
- Orchestrator, root and core lines are judged one command at a time, and the line takes the strictest verdict. A `cel ...` or `gh pr comment|review ...` command allows only itself.
- `CEL_GUARD_ALLOW_ONCE=1` on a line of its own leads no command and covers nothing after the newline.
- The guard strips the shell keywords in front of a command (`if`, `then`, `do`, `else`, `!`, `{`, ...) before matching it.

### Fixed
- A command after a newline got past every rule anchored at a command's start: `true` then `gh pr merge 3` on the next line was allowed for a solo agent; the same held for a builder's push to main, a read-only member's git write or `rm` of team records, core's `cel solo land`, `cel run member` and raw forge writes. So did `bash -c $'true\ngh pr merge 3'`. An orchestrator's `git checkout main` followed by a newline and any git write was allowed as a checkout move.
- `cel ...` or `gh pr comment|review|checks ...` anywhere in an orchestrator, root or core line allowed the whole line: `git push origin main && cel fleet`, `cel fleet; gh pr merge 3` and `gh pr comment 3 -b x; gh pr merge 3` were allowed.
- An orchestrator, root or core pane was refused a heredoc or multi-line quoted body that only spelled a refused command, for example `cat > .cel/notes.md <<'EOF'` with `gh pr merge` on a body line.
