### Fixed
- One Rex agent's runaway no longer ends every Rex agent. Every agent's processes lived in the Rex server's own systemd scope, whose default `OOMPolicy=stop` turned one out-of-memory kill (an agent's 18 GB test binary) into a stop of the whole scope: the server and every agent's program. Each managed Rex launch now runs its terminal's command through `systemd-run --user --scope` (exec'd in place, so the PID and receipt are unchanged) into a scope of its own, `cel-agent-<name>-…`, under `cel-agents.slice`, with `MemoryMax`, `MemorySwapMax` and `OOMPolicy=continue` (only the process the kernel chose dies); the slice carries `MemoryMax`/`MemoryHigh` across all agents. Defaults come from the box's RAM and swap (one agent 40% of RAM and 25% of swap, all agents 85% hard / 75% throttle) and box config `agent_memory:` (`max_mb`, `swap_max_mb`, `slice_max_mb`, `slice_high_mb`, `oom_policy`) overrides them. Without a systemd user manager a launch warns and runs in the server's cgroup as before. A Rex server cel starts (the safety net, the managed upgrade) now runs in a scope with `OOMPolicy=continue`.
- The user-manager calls on that launch path are bounded (`CEL_AGENT_MANAGER_TIMEOUT`, 5 s): a wedged manager falls back with a warning instead of hanging a launch, a resume or the steward's tick. Refused slice limits only warn - the agent still gets its own scope - and a `slice_high_mb` above `slice_max_mb` falls back to the defaults. A Rex server already running keeps its cgroup and `OOMPolicy` until it is moved into its own scope or restarted (README: "Rex agents' memory").
