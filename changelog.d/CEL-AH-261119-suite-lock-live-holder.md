### Fixed
- The steward's "suite lock held" alert names the process actually holding the lock. It used to read the pid from the lock file's first line and the age from its mtime, both left by whichever `tests/run.sh` last wrote them - so an external tool running `flock <lockfile> bun test` (which writes nothing) was reported as "held 1083m by pid <a pid long gone> (worktree unknown)". The holder is now the kernel's answer: the pid `/proc/locks` lists for the lock's inode when that process's fdinfo shows it holding the lock, else the oldest process with the file open (`fuser`, or a walk of `/proc/*/fd`) whose fdinfo does. The hold is dated from that process's start - or from when the steward first saw it holding, if it had already started while the lock was free or held by another - or, when the holder record matches the live holder's pid and start time, from when the record says the run took the lock. A holder with no matching record is named by pid, command and directory, and told to the owner of that directory (the same resolver as unledgered servers) as well as root. A lock nobody holds raises nothing, whatever the file says, and a holder record whose process is gone is deleted.
- `cel doctor` judges a suite lock leak by that same live holder, not by the pid in the file.
